# bookin

Ebook folder watcher and organizer. Watches `/input` for new ebook files, fetches metadata and cover art from the Hardcover API, and exports them to `/output` using a configurable Calibre Template Language pattern.

## Architecture

```
src/bookin/
├── cli.py            # Click entry point: --verbose
├── config.py         # Config dataclass; INPUT_DIR/OUTPUT_DIR constants
├── watcher.py        # watchdog daemon with file stability check + worker queue
├── processor.py      # Per-file pipeline: read → fetch → embed → add → export → delete
├── calibre.py        # Subprocess wrappers for calibredb and ebook-meta
├── hardcover.py      # Hardcover metadata client: lookup, ranking, field mapping, covers
├── graphql_client/   # GENERATED by ariadne-codegen, gitignored — never hand-edit
└── errors.py         # Exception hierarchy

vendor/hardcover-docs/     # SUBMODULE: Hardcover's schema.graphql (codegen input)
queries/*.graphql          # our GraphQL operations (codegen input)
```

**Processing pipeline** (one file):
1. `ebook-meta` → read embedded metadata (title, authors, ISBN)
2. `hardcover.fetch_metadata` → query the Hardcover API, rank matches, download cover into temp dir (best-effort)
3. `ebook-meta` → embed the fetched metadata and cover into the file (best-effort)
4. `calibredb add` → throwaway temp library
5. `calibredb export --template <cfg.template>` → write to `/output`
6. `calibredb remove` → drop the record from the temp library
7. Delete source file from `/input` (and prune emptied input subdirectories)
8. `shutil.rmtree` temp library

Calibre handles all template rendering and path sanitization natively — there is no custom template engine in this project.

## Key Design Decisions

- **Configuration via environment variables** — `BOOKIN_INPUT_DIR` (default: `/input`), `BOOKIN_OUTPUT_DIR` (default: `/output`), `BOOKIN_TEMPLATE` (default: `{authors} - {title}`), `BOOKIN_LOG_LEVEL` (default: `INFO`), and `BOOKIN_HARDCOVER_TOKEN` (the Hardcover API key; no default). No config file is used.
- **Hardcover is the only metadata source**, reached through a typed GraphQL client we generate ourselves — no Calibre metadata plugin is involved. Unlike Amazon/Google, Hardcover has a real API (not search-engine scraping), so it works from a container; Amazon was dropped for exactly that reason (`823563a`).
- **The GraphQL client is generated, not committed.** `ariadne-codegen` builds `src/bookin/graphql_client/` from `vendor/hardcover-docs/schema.graphql` plus `queries/*.graphql`. It is gitignored and produced on demand: the Makefile targets depend on it (so it rebuilds when an input changes), and CI and the Docker build generate it before installing the project. A fresh clone must run `make codegen` before `bookin` will import — that target also initialises the submodule, so `--recursive` is not required. Codegen validates the operations against the pinned schema, so a stale query fails the build. Queries deliberately use the *relational* columns (`contributions { author { name } }`, `book_series`, `image`) rather than Hardcover's `cached_*` `jsonb` columns, which would generate as `Any`. Every path is kept within Hardcover's max query depth of 3 — this is why the ISBN lookup filters `books` by their editions instead of querying `editions` directly.
- **The Hardcover API token is required and validated at startup** — supplied via `BOOKIN_HARDCOVER_TOKEN`, read straight from the environment (never stored on `Config`). `hardcover.verify_token` makes one minimal authenticated call (`me { id }`) before the daemon starts; a missing token or a 401/403 rejection is fatal (clear error, non-zero exit). If Hardcover is unreachable, validation warns and continues. The token lives only in the API client's Authorization header — never logged, never written to disk, never on a command line. Cover downloads deliberately use a *separate* unauthenticated client so the token is never sent to the asset host.
- **Matching is ours to tune.** `MATCH_THRESHOLD` (0.7) gates Jaro-Winkler similarity on title and weighted author score. Search relevance order is restored client-side because Hasura does not preserve `_in` ordering. Author scores are averaged over total *weight*, not contributor count — dividing by count (as the Calibre plugin does) lets a 2.0-weighted sole author exceed 1.0, so the check never rejects anything.
- **Throwaway Calibre library per file** — no persistent library is maintained. Each processed file creates and deletes its own temp library.
- **`QT_QPA_PLATFORM=offscreen`** is set in the Dockerfile. Calibre's CLI tools use Qt internally; this env var lets them run headlessly without Xvfb.
- **Metadata fetch failures are non-fatal** — if Hardcover returns nothing, the file is exported using only its embedded metadata.
- **Failed files** land in `/input/_failed/` with a `.error` sidecar containing the traceback — in the *input* tree, so `/output` holds only the finished library. `watcher._is_quarantined` excludes that directory from both the startup backfill and the event handler; without it a dead-lettered file would be re-queued, fail again, be moved again under a fresh name, and grow without bound. Retrying is manual: move the file back up into `/input`.

## Development

**Prerequisites:** `uv`, `calibre` (for local testing)

```bash
# Install calibre locally
brew install --cask calibre

# Install dependencies
uv sync

# Run daemon
uv run bookin
```

## Contributing

**Branch workflow:** When making changes, create a new branch and commit there. Do not commit directly to `main`.

```bash
git checkout -b <branch-name>
# make changes
git add <files>
git commit -m "description"
git push -u origin <branch-name>
```

Then create a PR on GitHub. CI (lint, typecheck, tests) and the Docker build must pass before merging.

## Commands

```bash
uv run pytest              # run tests
uv run ruff check .        # lint
uv run ruff format .       # format
uv run mypy src/           # type check
make codegen               # regenerate the Hardcover client
```

All must pass cleanly before committing (`make check` runs the lot). Tests mock all Calibre subprocess calls and intercept HTTP with `httpx.MockTransport` — neither a Calibre install nor a Hardcover token is needed to run them.

## Docker

```bash
docker compose up --build  # build and start
# drop ebooks into ./input/ — output appears in ./output/
```

Configuration is entirely via environment variables (see Key Design Decisions) — no config file is mounted.

## Adding Features

- **New Hardcover field:** add it to a fragment in `queries/fragments.graphql`, run `make codegen`, then map it in `hardcover.py:_build_metadata`
- **New metadata source:** add a module alongside `hardcover.py` and call it as a fallback from `processor.py:_process`. Note Amazon does not work from a container (see `823563a`); Google Books and Open Library do
- **New output behaviour:** modify `processor.py:_process` — the pipeline is sequential and easy to extend
- **New config field:** add to `Config` dataclass in `config.py` and read the corresponding env var in `load_config()`
- **New supported file type:** add the extension to `SUPPORTED_EXTENSIONS` in `config.py`

## Known Limitations

- No retry logic for transient Calibre failures — failed files go directly to `/input/_failed/` and are never retried automatically
- No rate limiting on the work queue — many simultaneous files will queue and process serially. Hardcover allows 60 req/min and we spend up to 2 per book; a 429 is retried once, then the book falls back to embedded metadata
- `ebook-meta` output parsing uses a line-by-line regex; may miss metadata if Calibre changes its output format
- The Hardcover schema is pinned to a submodule commit, with no automated freshness check. If Hardcover renames a field we select, lookups fail non-fatally and log `Hardcover lookup failed: ...` per book while metadata silently stops improving — `make update-schema` moves the pin and regenerates
- The `hardcover-docs` submodule is ~32 MB checked out for one 513 KB file; CI pays that on every run. The Dockerfile copies only `schema.graphql`, so the image is unaffected
- Edition language is filtered to `DEFAULT_LANGUAGES` (`eng`) in `hardcover.py`; not configurable via env yet
